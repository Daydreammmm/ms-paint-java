High Level Architecture:

	MVC
	To keep the code simple, a partial MVC was implemented.
	
	Model
	The Model captures enough information to re-draw the sketch of
	the user.
	
	View+Controller
	There is a View class as well as a few, what we call, view components.
	The View class containing the BorderPane as well as containing all of its components.
	View components are meant to be contained in the main View.
	Examples of view components are PaintPanel and ShapeChooserPanel.
	
	The View class, and view components all implements their own controller.
	For example, the PaintPanel listens to its own MouseEvents.
	This is instead of separating out the Controller from the View. This choice
	was made to simplify the code, yet still keep it modular and clear.
	
	Each view component can see the containing View as well as the Model
	as appropriate. This means that each view component can speak to the
	other view components. An example of this is when the ShapeChooserPanel
	buttons are clicked, resulting in a mode change in the PaintPanel.

by functionality such as redo to reflect seamlessly on the GUI whilst updating all the necessary components.

	Strategy: We implemented the strategy design pattern to manage the behavior and implementation of all the shapes
	that we can add to the canvas. We made a DrawingStrat interface that defines the methods that every each shape
	implements(some shapes don't implement certain methods eg: oval does not implement mouseMoved). Then we made a
	strategy class for each shape that implements the methods required to draw and preview the shape correctly. The
	implementation of the strategy pattern greatly introduces the code by enabling 4 things:
	1) Encapsulation: Each shape defines its own interaction and response to user input, and each shape is rendered
	differently despite using the same user input. Eg: the same action mouseDragged has a different implementation for
	the rectangle and oval strategies. Therefore, the PaintPanel can easily call the same event but display different
	implementations. This allows the PaintPanel to easily change drawing modes by changing the current strategy.
	2) Easy to understand code: The code is much easier for the team and other users to understand as there is clear
	segmentation between the implementations of each shape. Furthermore, debugging gets much easier because the bug can
	be isolated to a particular strategy. Lastly, the code in the PaintPanel reduces significantly, making the code
	less cluttered and long.
	3) Extensibility: New shapes can easily be added to the current application by adding a strategy for the shape,
	therefore the program is easy to scale up and improve.
	4) UI/Logic separation: The drawing logic is separate from the UI which leads to less code clutter and faster
	debugging. Furthermore, dependencies are reduced which is a good software development practice.
	These are the main advantages of implementing the strategy desing pattern in our program.

    Command:
    In our paint application, the undo/redo feature is essentially an implementation of the Command Pattern,
    even though we did not formally create Command classes.
    Whenever the user performs an action, such as adding a shape or deleting one, we create a small object that records
    everything needed to reverse that action later. This includes what type of change happened, which shape was
    involved, and where it was located in the list of shapes. This object acts like a “command.”
    We keep these command objects in a deque.
    When the user presses Undo, we look at the most recent command and perform the opposite operation.
    For example:
    If the action was “add shape,” undoing it means removing the shape.
    If the action was “delete shape,” undoing it means re-inserting the shape.
    After undoing, we move that command to the redo stack so it can be reapplied again if needed.
    When the user presses Redo, we simply re-execute the original command from the redo stack and move it back to the
    undo stack.
    This design matches the Command Pattern because:
    Each user action is stored as an object, separate from the model.
    The model acts as the Receiver, which actually performs add/remove operations.
    Undo and redo don’t need to know how shapes are stored or drawn—they only read the stored “command” information and
    apply the opposite or same action.
